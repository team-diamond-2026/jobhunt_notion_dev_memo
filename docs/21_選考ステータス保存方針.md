# 選考ステータス保存方針（#32）

決定日: 2026-11-14。親Issue [#6](https://github.com/team-diamond-2026/jobhunt_notion_dev_memo/issues/6)、後続 [#31](https://github.com/team-diamond-2026/jobhunt_notion_dev_memo/issues/31)、関連 #19 / #29 / #33。

## 決定

| 項目 | MVPの方針 | 理由 |
| --- | --- | --- |
| 現在状態の正本 | `companies.selection_status` のみ | 既存の企業一覧・詳細・編集・ボード・KPIが参照し、1行の更新で現在状態を管理できる |
| 管理単位 | 1企業につき現在の選考状態1つ | 職種/応募回/インターンと本選考を別々に管理する仕様は今回含めない |
| `applications` | テーブルを残すが、MVPアプリでは読取り・書込み・集計に使用しない | 現状のカラムだけでは応募単位・変更履歴の意味が定まらず、二重管理による不整合を避ける |
| 変更履歴の粒度 | 保存しない。現在状態と企業全体の最終更新日時だけを保持 | 各段階の到達時刻・変更理由・応募回別の状態はMVPの要件に含めない |
| 履歴表示 | 時系列の履歴一覧は実装しない | 詳細の進捗表示は現在位置の表示であり、過去に全段階を通った証拠ではない |

`companies.updated_at` はメモや企業名の編集でも変わるため、「ステータス変更日時」や「応募日時」の代わりに使わない。スキップした選考段階の到達日を推測して埋めない。既存の `applications` 行があっても、この決定に伴う削除・移行・上書きは行わない。

## 現行のステータス定義

DB制約・共通定数に合わせ、次の9値を保存する。

`未応募 → 応募済み → 書類選考中 → 一次面接 → 二次面接 → 最終面接 → 内定 → 不採用 → 辞退`

この並びは現行アプリの選択順と遷移判定順であり、すべての段階を順に通過するという意味ではない。

- `SELECTION_STATUS_OPTIONS` / `isSelectionStatus` / `canAdvanceSelectionStatus` を全更新経路で共用する。
- 現行ルールは同じ状態の保存と前方へのスキップを許可し、前の項目への変更を拒否する。新規企業は任意の有効値で登録でき、未指定時は「未応募」。
- 具体例: 一次面接→最終面接は可、最終面接→一次面接は不可、不採用→辞退は可、辞退→不採用は不可。内定→不採用/辞退も現在の判定では可。
- **今回、終端状態の特別扱いや訂正操作を追加しない。** #31が独自に終端ルールを導入しないよう、現行規則を仕様として固定する。訂正・再応募・終端ルールの見直しは、共通ヘルパー、全フォーム、KPI、移行方針を揃えた別の仕様変更として親 #6で追跡する。
- DBのCHECK制約は許可値だけを保証する。前後の遷移制約はアプリのサーバー処理で検証するもので、DBトリガーによる禁止とは区別する。

### 旧名称との対応

| 旧値/旧要件の名称 | 現在の扱い |
| --- | --- |
| 未エントリー、`not_entered` | 未応募 |
| ES提出 | 応募済み |
| Webテスト | 書類選考中 |
| 1次面接 | 一次面接 |
| 2次面接 | 二次面接 |
| お祈り | 不採用 |
| #6本文の「面接中」 | 一次面接・二次面接・最終面接の集約名。保存値ではない |

正規化は `202610030002_selection_status_options.sql` と `normalizeSelectionStatus` に対応する。旧名称を独立した保存値として再導入しない。DBに「面接中」などマッピング対象外の値があれば管理者が内容を確認して分類する。アプリの未知値→未応募の表示フォールバックを、データ移行や履歴復元の根拠にしない。

## #19のスキーマとの対応

| スキーマ/処理 | 確認した内容 | この方針との関係 |
| --- | --- | --- |
| `202606270001_mvp_schema_and_rls.sql` のcompanies | `user_id` / `workspace_id` / `selection_status` / `created_at` / `updated_at` | 所有企業の現在状態を保持する正本 |
| 同SQLのapplications | `id`, `company_id`, `status`, `applied_at`, `created_at`, `updated_at` | 企業FK、所有企業経由のRLS、updated_atトリガーがある。変更前/変更後/理由の履歴カラムや自動履歴追加トリガーはない |
| `202610030002_selection_status_options.sql` | companiesの旧値変換、defaultを未応募へ変更、9値のCHECK制約 | 初期スキーマだけでなく、この移行も対象環境に適用する。applicationsのstatusは変更しない |
| companiesのRLS | `user_id = auth.uid()`、書込み時は所有workspaceも確認 | ボードは認証済みクライアントを使用し、企業IDと所有者で絞る |
| `touch_companies_updated_at` | UPDATE時にDBでupdated_atを更新 | アプリから日時を渡してもDBトリガーが最終値を設定する |

`applications` は1企業に複数行を作れるが、行の存在だけで「応募1回」か「ステータス変更1回」かは決まらない。既存表をそのまま履歴表と呼ばない。将来採用するときは応募単位とイベント履歴を分けるかを先に決め、現在状態との整合をトランザクションで保証する。

## 現在の企業編集処理と、#31の保存契約

以下は **実装済みの事実** と **後続で実装する設計** を区別する。

### 現在の企業詳細/編集（main）

`app/src/app/companies/actions.ts` の `updateCompany` は、認証→企業所有者で現在状態を取得→有効値/前後関係を検証→UPDATE→詳細へ遷移する。UPDATEには企業名・業界・業界カテゴリ・志望度・選考状態・メモ・updated_atを含む。「ステータスだけを更新する処理」ではない。

- UPDATEの条件は企業IDとuser_id。読み取ったstatus/updated_atをUPDATE条件に含めず、更新対象を返して確認する処理もないため、競合検出を実装済みとは扱わない。
- 現行の保存エラーは例外。入力保持や再試行表示が全経路で完成しているとは扱わない。
- mainでは企業一覧・詳細を再検証する。#33のPR #69は詳細フォームを代替操作として使い、ボード再検証を追加する。

### #31で実装するボードの更新

1. 入力は企業ID、表示時の状態、更新先の状態、競合検出に使う表示時の `updated_at` とする。所有者は送信値ではなく認証情報から取る。
2. サーバーで所有企業の現在の状態・updated_atを再取得し、有効値と共通の遷移規則を検証する。表示時から変わっていたら競合として保存しない。
3. **ボード専用更新では `selection_status` だけをUPDATE** する。updated_atは既存DBトリガーに任せる。企業名・業界・メモ・applicationsには書き込まない。
4. UPDATE条件に `id`、`user_id`、取得した生の `selection_status` と `updated_at` を含め、更新後のid/status/updated_atを取得する。0行は成功ではなく、競合・削除・権限不一致として扱う。旧値を正規化した文字列でWHERE条件を作らない。
5. 更新結果を正としてボード表示を確定し、`/`、`/companies`、`/companies/board`、対象企業の詳細/編集を再検証する。同じ状態への移動は書込みせず表示を維持する。
6. 保存中は対象の再操作を抑止する。楽観表示を使う場合も、失敗時はDB成功を示さず、再取得した状態へ同期して理由と再試行導線を表示する。
7. 通信切断など結果不明時は、まず再取得して反映済みか確認する。再取得も失敗したら同期未確認と明示し、移動を重ねない。競合時は最新状態を示し、古い変更を自動で再送しない。

**既存フォームとの競合対策も #31の確認範囲。** ボードだけ条件付きUPDATEにしても、旧 `updateCompany` が後から上書きできる。詳細/編集フォームも表示時updated_atを送信し、所有者・現在状態・updated_atの条件付きUPDATEと結果確認へ揃える。これを実装するまでは、全更新経路での競合安全性を保証しない。#33の代替操作は同じフォームを使うため、この変更後に再確認する。

## #29・#33との整合

- KPIはapplications件数ではなく、所有企業の現在状態を集計する。未応募は未応募、面接中は一次/二次/最終面接、内定は内定。登録企業総数には不採用/辞退も含む。追加指標は #29で決める。
- 調査時点の未マージPR #59（head `9cfafa9`）は、ES提出/Webテストを独立した保存値として復活させ、書類選考中を除いた定義になっている。一方、mainのDB制約と本方針は9値であり、そのまま統合すると不整合になる。**#29/PR #59をマージする前に共通定数・集計をこの9値へ合わせる**。分類を変える場合は本方針とマイグレーション・既存データ移行を同時に見直す。#29完了は本Issueの前提ではない。
- #33は詳細フォームによる代替操作を採用済み（PR #69）。ボード専用保存や遷移規則の変更後は、スマホ幅で保存→再読み込みを再確認する。

## 確認結果と後続

2026-11-14にmain `4beeeb4` のアプリ参照箇所、共通ヘルパー、2つのSQL、既存フォームの更新列/WHERE条件/再検証先を照合した。`app/src` からapplicationsを読む/書く処理はなかった。

- Node.js 24のTypeScript直接実行で、現行ヘルパーの9×9遷移を照合し、45通りが許可・36通りが拒否された。7旧値の読み替え、不正な遷移先の拒否、DB制約と共通定数の9値一致も確認した。
- 一時PGlite 0.5.16へ実SQLを適用し、7旧値を含む合成企業を移行。移行SQLを2回適用しても成功し、新規企業のdefaultは未応募、旧値ES提出の再INSERTはCHECK制約（23514）で拒否された。既存applications行の全カラムは移行前後で不変だった。Supabase管理のauthオブジェクトは検証用の代替、pgcrypto宣言のみ省略して組込みUUID関数を使用した。対象Supabaseの適用・RLS・認証確認ではない。
- 変更文書のローカルリンク16件と `git diff --check` が成功。文書だけの変更のためアプリのlint/buildは再実行していない。
- #32は保存方針・責務・後続の契約を確定するIssueで、#31の実装や対象Supabaseの適用確認を完了扱いにしない。本PRはアプリの動作・DBデータを変更しない。
- #31では通常移動/同値/後退拒否、保存失敗、競合、別ユーザー、再読み込み、applicationsへの副作用なしを検証する。#23では対象Supabaseの移行・RLS・公開環境を確認する。
- 応募回別・職種別の管理、時系列履歴、到達日時、理由、訂正、履歴からの復元はMVP対象外。将来の履歴設計は親 #6で追跡し、着手時に専用Issueへ切り出す。
